協作流程規範

交付物交接鏈（Handoff Chain）
  • PO → Designer：用戶故事與功能流程完成後，設計師進行 UX 可行性審查，確認視覺設計方向與元件需求。
  • PO → QA（Left-Shift）：驗收條件撰寫後立即交 QA 審查，測試案例在開發啟動前完成，避免後期補測。
  • UX 研究員（平行軌道）：研究計畫與訪談指南獨立進行，不阻塞開發主軸，但研究洞察需在 Sprint 3 前完成匯入。
  • PM → 全員：每個 Sprint 結束前召開同步會議，確認下一 Sprint 範疇與優先順序。
Sprint 啟動前放行閘（Review Gates）
  • Sprint 0 啟動前：PO 用戶故事（US-101–US-405）經 Designer 與 QA 雙方確認無疑義。
  • Sprint 1 啟動前：公告模組 API 設計通過 QA 審查，設計稿（Wireframe）經 PO 簽核。
  • Sprint 2 啟動前：包裹通知與工單 UX 流程通過 UX Researcher 可用性評估，FCM 推播設計符合個資法規範。
  • Sprint 3（試驗上線）前：所有 P0 測試案例通過（Go/No-Go 檢查清單），試驗社區管理員完成入職訓練。
非同步優先溝通原則（Async-First）
  • 所有決策、討論與設計變更均以書面形式記錄於對應文件，避免口頭共識消失。
  • 技術問題優先開 GitHub Issue，設計問題優先在 Figma 留言，產品問題記錄於 user-stories.md 或 feature-flows.md。
  • 即時同步會議僅用於跨功能決策、Sprint 規劃及回顧，每次不超過 60 分鐘。
